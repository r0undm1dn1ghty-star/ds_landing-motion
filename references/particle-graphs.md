# Граф из сотен частиц — как не выглядеть картонно

Сцена: 200–400 узлов + связи + 10–20 хабов в кадре 600×600 (гифка для канала, hero-поле лендинга). Владелец формулирует дефект словами «точки выглядят чересчур векторно и свгшно», «картонно», «мыло».

## Причина провала

Первая версия — `circle` в SVG или `arc()` с `shadowBlur`/`filter: blur`: цветной круг плюс размытие. Такой примитив читается как «Glow из бесплатного пака», потому что:

- у него нет ядра — только пятно, глаз не находит точку фокуса;
- все элементы на одной плоскости — разница только в прозрачности, это не глубина;
- свечение одинаковое у всех — нет иерархии, нет «света».

Дорогое ощущение даёт точность, а не размытие: чем меньше blur при том же количестве точек, тем дороже кадр.

## Частица: три слоя

Рисуется как три наложения, все с `globalCompositeOperation='lighter'` (аддитивно светятся только яркие элементы, фон не мутнеет):

| слой | размер | alpha | примечание |
|---|---|---|---|
| ядро | `0.6–1.5 px` (растёт с глубиной) | `0.75–1.0` | почти белый `rgba(246,252,255,a)` |
| ободок | `ядро + 0.5 px`, только `stroke` | `0.35–0.75` | цвет стадии/категории, `lineWidth: .5` |
| bloom | `6–14 px` | `0.10–0.24` | ТОЛЬКО у ближних (`z > 0.55`), у дальних его нет |

Спрайты: 3 радиальных градиента на категорию, запечённые в offscreen-canvas один раз (ядро, bloom, пыль), дальше — `drawImage` с масштабом. `createRadialGradient` внутри цикла по 300 узлам на каждом кадре — гарантированный провал по времени.

## Глубина и параллакс

- `z ∈ [0.25, 1]` на узел (детерминированный hash от индекса, не `Math.random`).
- Позиция при наезде камеры: `p = target + (p0 - target) * (1 + (zoom-1)*(0.5 + 0.5*z))`. Дальние смещаются меньше — это и есть параллакс; «разная прозрачность без смещения» глубины не даёт.
- Порядок отрисовки — по возрастанию `z`, дальние первыми.
- Размер и alpha множатся на `z`; дальние тусклее и мельче.

## Состояние живёт в движении, а не только в цвете

Раскраска по категории на 300 узлах сама не читается — владелец говорит «потерялись цвета ниш». Каждому состоянию даётся СВОЯ грамматика движения, привязанная к общему времени `t` и к детерминированной фазе узла (`phase = hash(index)`; `Math.random` запрещён — кадр перестаёт быть воспроизводимым):

| состояние | поведение | как считается |
|---|---|---|
| живое / ранняя стадия | дышит и растёт | `pulse = .7 + .36*sin(1.55t + phase)`, радиус `r*(1.5)*(0.85 + 0.45*pulse)`, ядро почти белое, ободок гаснет на вдохе |
| среднее | шар: свет катается внутри | радиальный градиент со смещённым центром `ox,oy = cos/sin(0.42t + phase)*r*.36`; стопы: белый блик → цвет состояния → тень по краю |
| позднее / умирающее | мигает и проворачивается в чёрный | `f = .3 + .7*max(0, sin(2.1t + phase))`; ядро `rgb(210f+30, 70f+14, 64f+14)` — на провале почти чёрное, ободок гаснет вместе с ним |

Правила: состояния обязаны отличаться одновременно размером, яркостью и движением — одного цвета мало; пер-узловой `createRadialGradient` допустим только для «шаров» и только в офлайн-рендере (в живом виджете держать таких узлов меньше сотни на кадр); остальные состояния рисуются запечёнными спрайтами.

## Связность: поле, а не пыль

Симптом «не чувствуется, что я смотрю на 300 живых объектов» лечится связями, а не яркостью:

- локальная сетка внутри групп: сосед по рангу в той же группе и через один, если расстояние `< 78` / `< 110` px, alpha `0.05–0.10`, `lineWidth .32`;
- мягкое свечение в центре каждой группы (радиальный градиент `r≈90`, alpha `0.05`) — глаз собирает кластеры, поле перестаёт быть россыпью;
- межгрупповые связи остаются волосяными: alpha `0.012–0.11`.

Без локальной сетки и групповых свечений даже правильные частицы читаются как «случайный шум на фоне».

## Композиция

- Радиус = смысловая ось (например, стадия падения рынка), а не случайный разброс: 28 → 250 px шестью кольцами.
- Угол = сектор, но развёрнутый в спираль (`base + spread*1.4 - 0.7`), иначе получаются мёртвые секторы и «кольца».
- 200–300 микроточек пыли (`0.5–1.2 px`, alpha `0.04–0.14`) — фон перестаёт быть пустым, кадр перестаёт выглядеть схемой.
- Связи — волосяные: `lineWidth: .42–.6` БЕЗ масштабирования от зума, alpha `0.012 + 0.1*near`, где `near = 1 - dist/560`. Градиент на каждую связь не нужен и дорог: плоский `strokeStyle` с alpha читается так же.
- Зерно 3–5 % и виньетка поверх — убирают бандинг в тёмном поле и дают «плёночность». В версии под GIF зерно ВЫКЛЮЧИТЬ (параметр `?g=0`): оно и есть основной вес файла и убивает межкадровое сжатие; в MP4 его можно оставить.

## Таймлайн (10 секунд, финал держится долго)

| фаза | время | что происходит |
|---|---|---|
| вход | 0–1.0 s | одна группа, `opacity 0 → 1`, без стаггера |
| наезд | 1.0–5.0 s | `easeOutCubic`, zoom `1 → 2.6` к целевому узлу |
| фокус | 4.2–5.6 s | хабы притухают до 30 %, виньетка вокруг цели |
| карточка | 5.3–6.2 s | выезд `translateX(16px) → 0` + fade |
| холд | 6.2–9.6 s | НИЧЕГО не движется, кроме одного пульса на цели |

Холд на финале — обязательная часть, если кадр уходит в канал: зритель должен успеть прочитать карточку. 3–4 секунды холда минимум; «мелькнуло и закончилось» = переделывать.

Счётчик анимаций держать ≤10: `document.getAnimations().length`. На 300 узлах сорок входных анимаций дают «ёлочку» (см. запрет 16 в SKILL.md).

## Съём кадров в GIF

Два рабочих пути, оба детерминированные:

1. **CSS-анимации:** перед съёмом `document.getAnimations().forEach(a => a.pause())`, затем на каждый кадр `a.currentTime = ms`. Кадр = чистая функция времени, повторный прогон даёт тот же пиксель.
2. **Canvas-сцена:** отдать в страницу параметр `?t=3.5`, который вызывает `render(t)` и НЕ запускает `requestAnimationFrame`. Дальше — по одному запуску headless Chrome на кадр:

```bash
"C:/Program Files/Google/Chrome/Application/chrome.exe" --headless=new --disable-gpu --hide-scrollbars \
  --force-device-scale-factor=1 --window-size=600,600 --virtual-time-budget=4000 \
  --screenshot="out/f042.png" "file:///.../field.html?t=4.2"
```

Питфоллы съёма:

- **Самый быстрый съём — ОДИН живой Chrome через CDP; запуск процесса на кадр — самый медленный.** `chrome --headless --screenshot=<url?t=…>` на каждый кадр стоит 2–5 с (старт процесса + парсинг): 72 кадра упираются в потолок инструмента (420 с) и сборка умирает на середине. `canvas.toDataURL()` из `Runtime.evaluate` тоже отваливается на тяжёлой сцене (лимит ответа 5 с). Рабочая схема: поднять Chrome один раз с `--remote-debugging-port=<port> --user-data-dir=<tmp>`, взять `webSocketDebuggerUrl` из `http://127.0.0.1:<port>/json` и на каждый `t` делать `Page.navigate` + `Page.captureScreenshot` — ~0.3–0.5 с на кадр (`websockets` + `requests` в окружении есть). Упрощение кадра тоже ускоряет: плоский `strokeStyle` вместо `createLinearGradient` на каждую связь.
- **60 кадров х 600 px на телефоне читаются как мыло.** Рендерить в 1,5×: канвас `600*S` пикселей при `document.documentElement.style.zoom = S`, вьюпорт Chrome `--window-size=900,900`. Телега ужимает до ширины экрана — ядра остаются острыми. Резать разрешение ради веса = лечить симптом не с той стороны.
- **Вьюпорт Chrome ниже окна на ~96 px.** `--window-size=900,900` даёт `innerHeight≈804`: низ композиции (карточка, подпись, кнопки) срезается, на кадре пустой низ, а `y + height` оверлея больше высоты окна. Запрашивать `--window-size=W,H+120` и обрезать каждый кадр до `W×H` (`Image.crop((0,0,W,H))`), а не доверять размеру окна.
- **Вес:** 900 px / 76 кадров с адаптивной палитрой ПО КАЖДОМУ кадру и зерном — ~29 МБ; `palettegen(stats_mode=diff)` + `paletteuse(dither=none, diff_mode=rectangle)` без зерна (`?g=0`) — ~10 МБ на 800 px. Тёмная сцена с градиентами в GIF не сжимается: если после `dither=none` и отключённого зерна всё ещё >5 МБ — не резать fps и размер дальше, а отдавать **MP4** (беззвучный H.264 `crf 19`, `+faststart`): TG играет его как гифку, вес в 5–10 раз меньше. Приёмы экспорта — скилл `tg-loop-gifs`.
- **Резкость перед квантованием стоит ~25 % веса.** `UnsharpMask(radius≈1.3, percent≈70–75)` по 600-пиксельным кадрам: 160 цветов → 6.8 МБ, 112 → 6.0, 96 → 5.5, 64 → 4.6 (72 кадра, 7.6 fps). Подбирать цвета лестницей и отдавать два файла — HQ (112–160) и light (64): TG тянет анимации до 50 МБ, «5 МБ» — запас на ленту, а не жёсткий лимит.

## Карточка в кадре

Кадр с карточкой — это не фон с подписью, а носитель смысла; владелец читает её как продукт.

- Подложка плотная (`#080c13`), по центру, ширина ~520 из 600, тень глубокая. Прозрачная подложка «мешает»: частицы просвечивают через текст.
- Структура сверху вниз: строка состояния (ниша · стадия X из 5 · остаток срока) → заголовок → вердикт одной фразой → 2×2 ударных цифр с источником и датой мелким моно → шкала срока жизни (6 сегментов по стадиям, текущий горит, белая риска «сейчас») → две колонки «факторы смерти» и «кто забирает» → строки «вход» и «выход».
- Каждая цифра несёт источник и дату прямо под собой (`2ГИС · 02.2026`); цифра без источника в кадре не живёт.
- Проверка влезания: страница принимает `?measure`, пишет `getBoundingClientRect()` карточки в `document.title`, читается `--dump-dom` + regex `MEASURE\{...\}`; условие приёмки `y + height ≤ высота кадра` и `height ≤ 0.85 * высота`.

## Приёмка числами

- **Резкость** (доля пикселей с яркостью > 200) на кадре графа: 0.1–0.5 %. Ноль — ядра слишком тусклые, ядро не читается; больше 2 % — каша пересвета.
- **Заполнение:** контурная энергия (`ImageFilter.FIND_EDGES`, среднее) 2–4; ниже 1.5 — сцена почти невидима.
- **Цвет видно?** Считать долю пикселей по диапазонам: красные `r>90 && r>g+35 && r>b+25`, жёлтые `r>90 && g>70 && b<g-25`, зелёные `g>90 && g>r+25`. Живой кадр даёт 0.1–0.6 % на каждый диапазон; 0 % в любом = цвет утонул в фоне и состояние не читается.
- **Чернила по регионам** — граф 10–18 %, карточка 6–10 %; 0 % в регионе = блок пуст.
- **Уникальность кадров:** md5 по кадрам, 55+ из 60 уникальных; подряд идущие дубли допустимы только на холде.

## Язык для отчёта владельцу

Не «сделал красивее», а что физически изменилось: «цветной круг с blur → белое ядро 1 px + ободок 0,5 px + след свечения только у ближних», «одна плоскость → три плана с параллаксом», «4 секунды холда на финале». Он оценивает формулировки через результат, поэтому цифры и слои перечислять явно.
