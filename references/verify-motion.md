# verify-motion — как доказать, что эффект работает, а не «выглядит норм»

Порядок: снять кадр до выводов → измерить DOM → измерить пиксели → сверить с ожидаемыми числами. Всё, что ниже, проверено прогоном `demo/measure.py` на Chrome 141 (headless=new, Windows 11).

## 1. Прогон: что запускать

```
python demo/measure.py --shot-dir <папка для кадров> [--json out.json]
```

Харнесс делает 4 прогона одной страницы (`?static=1&final=1&tier=webgl2|canvas2d`, `&reduce=1`, без `tier`), снимает 3 кадра (полный десктоп, вьюпорт, мобильная обёртка 390), считает статистику областей и печатает гейт приёмки. Код запуска Chrome в нём же — копируй из `measure.py::run_chrome`.

Ключи страницы, без которых прогон не сойдётся:

| Ключ | Зачем |
|---|---|
| `?static=1` | выключает бесконечные циклы (частицы, авто-вращение) — иначе виртуальное время не доходит до таймеров |
| `?final=1` | через 3.2 с делает `finish()` всем анимациям: кадр показывает финальное состояние |
| `?tier=webgl2\|canvas2d` | фиксирует путь эффекта: GPU-ветка через `requestAdapter()` замораживает виртуальное время (см. §5) |
| `?reduce=1` | добавляет класс `force-reduce` — reduce-ветка проверяется без CDP-эмуляции медиазапроса |

## 2. Ловушки headless, из-за которых «страница сломана» — ложный вывод

1. **Клок анимаций не идёт.** Под `--virtual-time-budget` CSS-переходы и `@keyframes` остаются на первом кадре: `stroke-dashoffset` держится на стартовом значении, `transition` не доезжает. Поэтому:
   - линию рисуй через WAAPI (`element.animate(...)`) и проверяй **сиком**: `el.getAnimations().forEach(a => a.finish())`, затем читай `getComputedStyle(el).strokeDashoffset`; в демо это дало `98px → 0px`;
   - состояния, которые включаются классом с `transition`, читай **со снятым переходом**: `el.style.transition='none'` → `getComputedStyle(el).transform` → вернуть. Иначе обе позы вернут стартовую матрицу (`matrix(1, 0, 0, 1, 0, 0)` при непустых переменных — типичный симптом);
   - не давай `finish()` прокруточным анимациям: у них таймлайн `ViewTimeline`/`ScrollTimeline`, и `finish()` защёлкивает кадр на конце. Пропускать по `a.timeline.constructor.name`.
2. **`--window-size` не задаёт layout-вьюпорт для мобильной ширины.** Проба ширины — iframe фиксированной ширины (в `measure.py::mobile_probe`): `clientW` внутри обёртки обязан совпасть с шириной iframe (в прогоне `clientW=375` при iframe 390 — это скроллбар iframe, не баг).
3. **Прокрутка.** `html{scroll-behavior:smooth}` — `scrollTo` не докручивается под виртуальным временем: ставь `document.documentElement.style.scrollBehavior='auto'` на время пробы. После `scrollTo` позиция применяется сразу, а **прогресс `ViewTimeline` пересчитывается в следующем кадре** — читать с задержкой ≥300 мс (`381px → 0px` только на отложенном чтении).
4. **`IntersectionObserver` не срабатывает для того, что ниже первого экрана.** Reveal-классы и триггеры надо дублировать таймаутом ~2.5 с; тогда кадр показывает финал, а не пустоту.
5. **`navigator.gpu.requestAdapter()` под виртуальным временем не завершается** — ни `.then`, ни `.catch`, ни `setTimeout`-страж. Симптом: узел с числами остаётся `null`/`pending`, хотя остальная страница прожила все таймеры. Вывод: WebGPU-ветку в headless-прогоне фиксируй параметром (`?tier=webgl2`), а сам WebGPU-путь проверяй в реальном браузере (см. §6).

## 3. Что мерить в DOM

- **Переполнение по X** — единственное честное доказательство: снять маскировку `overflow-x`, затем `scrollWidth - clientWidth` и список узлов с `getBoundingClientRect().right > clientWidth+1`. В прогоне: `overflowX=0`, `offenders=[]` на 1422 и на 375.
- **Слои глубины** — `translateZ` читается из матрицы: `m43` (`matrix3d` → индекс 14). Числа демо: `back -56 · mid -8 · front 58`.
- **Перспектива доказана не CSS, а геометрией**: `rectFront.width > rectInner.width` (263 против 246 при `perspective:900px` и `translateZ(58px)`).
- **Состояния** — не строку матрицы, а разобранные числа: у частей `{dx, dy, rot}` из `matrix(a,b,c,d,e,f)`; тогда «в сборе» и «в разлёте» сравниваются, а не «похожи на строку».
- **Спрайт-лист** — `getComputedStyle(host).backgroundPositionX` на двух кадрах: `-1584px` против `-3696px` = кадры разные.
- **Канвас** — отношение `canvas.width / clientWidth` должно быть 1.0 (в демо так); `2.0` = отрисовка в `devicePixelRatio` без нужды.

## 4. Что мерить в пикселях

- `gl.readPixels` **внутри страницы** (с `preserveDrawingBuffer: true`) даёт числа без внешних библиотек: mean/std кадра и диф между двумя состояниями. Демо: `dispFlat 0.1017 → dispRelief 0.1043`, `diff mean 0.0225 / max 0.503 / 12.5% пикселей изменены >12 уровней` — это доказательство, что дисплейсмент меняет геометрию, а не только множитель.
- Три режима печати различаются: `halftone mean 0.582 std 0.206`, `дизеринг mean 0.586 std 0.240`, `зерно mean 0.143 std 0.077`, `halftone vs дизеринг: 38% пикселей изменено`.
- **PNG-области** через Pillow: mean/std по прямоугольнику секции (координаты берутся из `getBoundingClientRect` + `pageYOffset`, собранные страницей в `report.rects`). Пустая область = `std ≈ 0`; в демо минимум по областям `std 9.4` (SVG), максимум `std 61.1` (halftone-печать).
- Зерно: без числа «видно/не видно» не решается. `mix-blend-mode: overlay` на тёмном фоне съедает слабый шум — если std полосы не выше 1–2 уровней, зерна нет.

## 6. Реальный браузер вместо headless

Когда нужно живое время (переходы, шрифты, WebGPU) — открывай страницу в настоящем браузере и читай те же узлы: `document.querySelector('#probe').textContent` (демо пишет туда JSON), `getComputedStyle`, `el.getAnimations()`, `a.effect.getComputedTiming().progress`. Под `file://` браузер запрещает чтение `document.styleSheets[0].cssRules` (`SecurityError`) — вычисленные стили читаются, список правил нет; вместо разбора правил используй CDP `CSS.getMatchedStylesForNode`: он показывает, какие правила реально применились (так в этом прогоне нашлась селекторная ошибка `.svg-in .flow` против `.flow.svg-in`).

**Реальный браузер — ещё и арбитр по «пустым блокам».** Часть содержимого под виртуальным временем просто не появляется, и headless-замер объявляет рабочий блок мёртвым:
- фон-картинка из data-URL (`host.style.backgroundImage = 'url(' + canvas.toDataURL(...) + ')'`) не успевает декодироваться: блок честно мерится как `0.0 %` пикселей, а в живом браузере даёт `60 %` и рисуется. Не чинить то, что не сломано;
- цифра из прогона — это факт о ПРОГОНЕ, а не о странице.

Рецепт ground truth (полный кадр любой высоты):
1. `Emulation.setDeviceMetricsOverride` — ширина/высота до нужной (например `1440 × 4700`), `deviceScaleFactor: 1`, `mobile: false`;
2. пауза ~2 с на декод картинок, шрифты и кадры циклов;
3. `Page.captureScreenshot` с `captureBeyondViewport: true`;
4. координаты блоков брать свежим `getBoundingClientRect()` из того же документа — координаты из headless-пробы после смены вьюпорта не годятся.

Две ловушки самой съёмки, обе выглядят как дефект страницы: `Page.captureScreenshot` с `clip`, лежащий ВНЕ вьюпорта, возвращает ровный кадр без ошибки; скрытое/невидимое окно отдаёт чёрные кадры любого размера. Прежде чем объявлять блок сломанным — снять полную страницу и посмотреть на неё.

## 7. Проверка глазами и её цена

`vision_analyze` годен как детектор дефектов (обрезка, наложение, пустая область) и **не годен как судья стиля**. На кадре этого демо он заявил «фиолетовые градиенты, glow-облака, пилюли, карточки в карточках, иконка над заголовком». Пиксель-скан: 0.92 % голубоватых пикселей — это ночное небо внутри canvas-пейзажа (свой цвет сцены), топ-8 цветов кадра — токены бренда (`#111524`, `#151927`, `#0d1120`). DOM: `border-radius` у всех кнопок `10px`, пилюль (`999px`) — 0, вложенных карточек — 0, иконок над заголовками — 0. Каждое цветовое и геометрическое утверждение модели проверяется пиксель-сканом или `getComputedStyle` до правки.

**Глаз ловит то, чего числа не видят, поэтому оба прохода обязательны.** В одном прогоне модель выдала и ложный сигнал, и настоящий дефект:
- *ложный*: заявила обрезку текста на мобильной ширине — проба через iframe дала `ovf=0 offenders=[] smallText=[]`, то есть текст не обрезан, а описана была подсказка;
- *настоящий*: чёрные прямоугольники на месте двух канвасов. Проба при этом показывала честные 1574 сегмента — числа считались и не рисовались.

Правило: находка модели — это СЛЕД, а не вывод. Каждую проверять замером (пиксель-скан, `getComputedStyle`, проба переполнения), но визуальный проход не пропускать: пустой канвас числовым проверкам невидим.

## 8. Гейт приёмки (что считается доказанным)

`demo/measure.py` печатает список проверок и слово «пройден» только при всех: проба читается; `overflowX=0`; дисплейсмент меняет >1 % пикселей; три режима печати различаются >5 % пикселей; line-draw доходит до `0px`; трасса скроллом меняет `dashoffset`; морфинг меняет bbox; разлёт меняет позы; поворот двигает `spin`; спрайт-лист шагает; переменные двигают панель; фолбэк `canvas 2d` поднимается; reduce отдаёт финальное состояние; кадр снят; мобильная проба `ovf=0`.

Приёмы 10–13 на той же странице (контуры, гравировка, детерминированный кадр, прибор ритма) добавляют свои проверки в тот же список, и поверх них — **видимость каждого блока**: `ink_by_region()` считает долю пикселей выше фона по областям кадра, проверка «ни один блок не пустой» падает при пороге 2 %. Всего проверок 26.

## 9. Четыре ловушки самой съёмки и замера

1. **`--screenshot=` молча ничего не пишет.** Относительный путь или смешанные разделители (`demo/_shots\shot.png`, как получается из `os.path.join` при POSIX-части пути) — Chrome возвращает код 0 и файла не создаёт, ошибки нет. Симптом обманчив: в отчёте пустая строка `кадры :`, гейт падает на «кадр снят», а на диске лежат кадры ПРОШЛОГО прогона — и кажется, что съёмка работает. Правило: `--shot-dir` приводить к абсолютному (`os.path.abspath`), а в аргумент Chrome отдавать путь с прямыми слешами (`p.replace('\\', '/')`).
2. **Проверка мерит ГЕОМЕТРИЮ, а не разбирает computed-строку.** `getComputedStyle(el).inset` возвращает проценты в пикселях (`-117.109px`), поэтому поиск подстроки `-12%` даёт ложный провал. И отношение `getBoundingClientRect().width` у элементов с `preserveAspectRatio: slice` даёт ровно 1.0 при реальном вылете за контейнер. Мерить дельту в пикселях одного и того же края: `layer.left - container.left` (в прогоне `-115px` — вылет подтверждён). Общее правило: у проверки должно быть ЧИСЛО с порогом, а не совпадение строки.
3. **Статический кадр без кадрового цикла не даёт чисел.** Рисуется один раз — прибор движения покажет окно из одного кадра и нулевую медиану, и проверка «прибор отдаёт числа» пройдёт на мусоре. Решение: разнести рисование в `paint(t)` и замер в `step(t, dt)`, а в статическом режиме прогнать `step()` фиксированным шагом (в прогоне 90 итераций по 1/60 с) — та же математика, честные числа, заполненное окно. И порог проверки ставить содержательный (`median > 0 and window >= 60`), а не `is not None`.
4. **Проба показывает числа при пустом экране.** Канвас отдаёт `coverage 17.5%` из своего буфера, а на странице — ровный фон: смена `canvas.width/height` ОЧИЩАЕТ буфер, и если размер переназначили без перерисовки, блок мёртв при живых числах. Признак: доля видимых пикселей в области на кадре ≈ равна площади одного шильдика. Лечение: любой ресайз (включая `ResizeObserver`) обязан перерисовать; проверять не пробу, а `ink_by_region()` из `demo/measure.py`.
